# Core 架构

Core 是单 Cargo 库包 `recuvora-core`，公开顶层模块只有 `operation` 与 `recovery`。它根据领域状态、可信配置和显式输入计算状态迁移，返回待提交变更与确认后的操作意图。本库不执行 I/O、不读取系统时钟，也不启动任务或调用外部服务。

## 领域接口

| 接口 | 输入与输出 |
| --- | --- |
| `IncidentLedger` | 观察、当前时间与已提交历史，计算故障和检查点提案 |
| `ApprovalLedger` | 完整操作、当前政策、审核与结果事实，计算审批提案及确认后的一次许可 |
| `KnowledgeState` | 可信 `RepairExperience` 与容量命令，计算经验提案、精确检索、不可变产物和永久隔离 |
| `RecoveryState` | 故障、观察、经验、审批、动作与结果事实，计算统一 Harness 请求、结果及独立总结提案 |
| `Prepared`、`CommitRequest`、`CommitReceipt` | 待提交结果、完整输入绑定及可靠提交的确认 |

各模块的接口细节见[源码导航](../src/README.md)。恢复配置只接受 schema 2，历史恢复使用当前协议的完整事件与原配置。

## 显式输入与信任

时间、当前观察、目标所有权、审核身份和执行证据全部通过输入传递。`execution_harness`、`executor_id` 等逻辑身份参与规则绑定与审计，不表示具体服务连接。配置不包含连接地址、节点工作区或提供方实现。

模型报告和候选动作不产生权威事实；人工决定也必须通过当前硬政策。提交回执与可信经验断言要求调用方已有可靠证据，类型校验本身不认证调用方，也不证明证据真实。接口使用前提见[调用契约](calling-contract.md)。

## 提案与确认

一次计算不会改变调用方持有的旧聚合。`Prepared` 保存候选状态和提交请求；只有匹配的 `CommitReceipt` 经 `confirm` 校验后，才返回新状态及操作意图。

`CommitRequest` 绑定提交 ID、领域、原记录版本、新记录版本和完整逻辑输入。调用方必须原子比较 `expected_revision` 并可靠保存完整变更，随后才能确认；同 ID 不同内容必须拒绝，相同内容也不能重复释放一次执行副作用。发送成功、缓冲写入或超时都不是可靠提交的证明。

历史恢复与实时迁移共用领域校验，但不返回执行许可或外部操作。删减、重新编号并重新计算摘要的历史无法暴露被隐藏的旧事实，因此完整可信历史是恢复入口的前提。历史绑定及跨域提交顺序见[领域维护](domain-maintenance.md)。

## 动作、结果与经验

`RepairArtifact` 是提供方中立的不可变动作内容。Core 校验通用格式、来源、前提、允许的动作种类及一次动作预算，不解释具体语言或平台。执行回执须精确绑定已提交动作；经验命中与总结候选均不授予执行权限。

执行回执、独立业务验收和经验交付分别表达。Unknown 需要独立执行证据，当前业务健康不能证明原操作是否运行，取消或断连也不证明执行者停止。恢复结果、失败或 Unknown 的实际动作隔离及待总结经验共同提交；总结失败不改变已确认的业务终态。完整状态迁移见[恢复流程](recovery.md)。
