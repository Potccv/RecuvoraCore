# 领域维护与 Host 提交

Core 计算领域状态并校验完整历史；Host 选择持久保存和跨模块对接方式。本文规定接入时的提交顺序、并发边界与维护义务，不提供文件安装、数据库迁移或应用运维命令。版本接入变化见[Host 接入迁移](host-boundary-migration.md)。

## 持久提交与历史恢复

Host 保存提案所需的完整事件或命令、原始可信配置及提交身份，原子比较 `CommitRequest.expected_revision` 后持久提交，再通过 `CommitReceipt::confirmed` 确认。请求同时绑定领域和逻辑输入；同 ID 的内容冲突必须拒绝。提交结果不确定时先核实持久事实，不安装推测的新状态，不重新发放已消费许可。

| 领域 | 传输与恢复入口 |
| --- | --- |
| 故障 | `IncidentLedger::entries` 输出 `IncidentEntry`，`restore` 校验顺序和完整观察事务 |
| 审批 | `ApprovalLedger::entries` 输出 `ApprovalEntry`，`restore` 校验操作、政策、审核与一次消费事实 |
| 恢复编排 | `RecoveryState::entries` 输出 `RecoveryEntry`，`restore` 重复状态迁移及操作、证据关联校验 |
| 经验 | `KnowledgeCommand` 可序列化；`snapshot` 输出完整查询数据；`replay` 使用可信重建的 `KnowledgeReplayEntry` 重复命令与确认校验 |

可反序列化的事件和查询记录不是外部调用方直接安装权威状态的权限。Host 只从受保护的完整已提交历史调用恢复入口，不把模型输出或外部知识响应当作本地历史。可信验收和提交确认没有直接反序列化入口；知识查询快照也不能直接替代已验证命令重放。

审批恢复后通过 `prepare_recovery` 提交恢复转换；恢复编排在 `restore` 后要求先提交 `RecoveryEvent::Recover`，再接受后续变更。中断执行继续阻塞并按 Unknown 处理；待审批任务进入 `Paused`，需要显式 `Resume`。恢复不重新发出原执行许可，也不自动重复外部动作。具体阶段见[恢复流程](recovery.md)。

## 样本与独立故障轮次

`ProblemContext.occurrences` 表示单个故障轮次中的异常样本数。`RecoveryTask.episode_count` 根据相同目标、故障指纹和条件的历史不同故障身份计算；同一故障重复登记不增加轮次，样本数增长也不增加轮次。

新任务以 `IncidentEvidence` 绑定当前活动故障及其记录版本号。`minimum_script_occurrences` 使用独立故障轮次，约束经验复用资格及当前任务选择复用方案。Host 不得通过删除旧故障、重新分配身份或裁剪历史改变轮次，旧版本数据导入不能只用观察样本数重建独立轮次。

## 共享目标所有权

Host 将同一受保护目标的别名归一到稳定逻辑身份，并在相关审批、恢复聚合和执行者之间维持排他的目标所有权。`TargetAuthority { target_id, epoch }` 只是 Host 提供给 Core 的身份绑定，Core 不获取租约、不设置文件锁，也不验证跨进程锁服务。

Host 在消费审批许可、提交恢复执行授权和实际派发之间持有同一有效所有权，并保证当前故障记录版本和活动状态在该边界内不会失效。可以使用统一事务或覆盖整个边界的可信并发门控；不能在普通读取之后无保护地执行。所有权代次改变或故障已解除时，不能使用旧提案继续派发。

异常退出、超时、取消与连接断开不证明执行者停止。Host 应保留存在执行意图、Unknown、未确认在途调用或不确定提交的目标归属，直到核实对应事实；释放前停止新派发、等待在途调用结束并确认没有剩余执行权威。Core 的内存互斥判定只覆盖提供给它的聚合，不能替代多个 Host 实例之间的排他协调。

## 跨域提交顺序

1. 先提交恢复任务中的原始 `ProposedOperation`，确认后处理 `RecoveryEffect::RequestApproval`。Host 用完整操作查找或创建审批，再提交恢复域的 `ApprovalAttached`。在两域提交之间中断时，按原操作身份查找已有审批，不能生成新操作或重复审批。
2. Host 完成当前故障、环境、硬政策和目标归属检查，在保持并发门控的条件下提交审批 `Consume`。确认得到 `ExecutionPermit` 后，把许可移入 `RecoveryCommand::AuthorizeExecution`；只有恢复授权也可靠提交并确认后，才处理 `RecoveryEffect::Execute`。
3. Host 保留该不可复制许可直到执行回执可提交，通过 `ApprovalLedger::prepare_complete` 先提交审批执行结果，再把对应审批事实和回执交给恢复域的 `ExecutionRecorded`。之后的业务验收独立提交，脚本退出成功本身不是业务成功。
4. Unknown 核实时，Host 先把独立执行证据和业务验收作为 `ResultChecked` 提交到恢复域；审批仍是 Unknown 时只保存证据，不产生最终交付或释放结果。随后以这些已验证证据提交审批 `Reconcile`，再用同一组证据和更新后的记录版本、审批事实提交 `ResultChecked`，最终完成流程。

这些步骤不假设多个存储天然支持同一事务。Host 必须保留跨域关联和中断时的已有事实，不把某一域的状态当成另一域已经提交的证明。目标当前健康不能代替独立执行证据，确认未执行也不能自动重发原许可。

## 经验交付与隔离

恢复域在确认业务结果时同时记录稳定的 `KnowledgeDelivery`。失败或 Unknown 对应的脚本版本隔离事实在恢复域先提交，之后才允许推进，因而知识存储不可用不会重新开放有风险的复用。已经结束的业务任务不因经验尚未交付而继续占据未结束任务位置；Unknown 本身仍保持阻塞。

Host 从确认后的 `DeliverKnowledge` 或 `pending_deliveries` 读取待交付数据，按原候选、案例和操作身份提交知识命令。成功案例需要可信 Host 根据独立验收显式构造 `TrustedBusinessVerification`。只有知识域可靠提交后才提交恢复域 `DeliveryConfirmed`；交付重试不能再次执行脚本，也不能删除已发生的失败隔离。

知识案例按同一候选的记录时间有序提交。Host 应保持相同候选的交付顺序并使用全局案例幂等键；故障、业务结果和后续核实的交付记录不得因外部存储重试而改写身份。知识规则及容量范围见[知识库接口](../src/recovery/knowledge/README.md)。

## 数据维护

备份、索引、物理压缩、归档、存储容量扩展、安装和配置切换属于 Host。Core 保留集合容量和输入大小等逻辑限制，不报告文件字节或自动清理历史；请求配置参与内容绑定，改变历史配置不能被当作普通恢复。

维护必须保留操作身份、审批关联、一次消费、案例幂等键、不可变脚本内容及失败、Unknown、禁用和隔离事实。保留事件顺序与独立故障轮次，不能通过删除旧记录或重编号来绕过容量或授权限制。当前没有通用历史裁剪或在线配置迁移入口。

Host 在冻结来源、核实全部在途调用和提交结果之后准备维护输出，再用对应领域恢复入口校验。校验失败时保留原可信历史，不安装部分结果，不截断损坏数据，也不重放外部动作。纯领域回放成功不证明存储事务、跨进程所有权或真实业务恢复已验收；证据范围见[测试与验证](testing.md)。

## 执行提交的并发条件

Host 在审批消费与流程派发提交期间必须保持目标所有权，并原子核验当前故障、审批记录版本及知识隔离状态。传入 Core 的不可变快照只证明本次计算使用了哪些事实，不能保证提交时其它实例没有改变这些事实；使用事务条件或可信互斥边界处理该间隙。

审批许可已经消费但流程派发准备失败时，不得把“没有发出动作”直接记录为普通执行失败并丢弃原关联。Host 先将审批保守转 Unknown，再将关联结果输入流程，提交独立的未执行证据，最后执行审批核实与流程终结。已经终结的审批在任务回执缺失时也可通过 ApprovalAttached 或 ApprovalResolved 进入 Unknown 核实路径，不重新发放许可。

同一候选的经验按 `KnowledgeDelivery.created_revision` 的产生顺序交付。`pending_deliveries` 按该顺序返回；有早期积压时，新的交付效果仍指向最早待交付案例。早期案例未确认时拒绝确认后来的案例，避免跳过 Unknown 或失败事实。Host 不能绕过该顺序直接把后期结果写入知识模块。
