# 恢复流程

恢复流程维护排队（Queued）、诊断（Diagnosing）、等待审批（AwaitingApproval）、执行（Executing）、验收（Verifying）、保存修复经验（Publishing）及最终状态；暂停（Paused）需要显式恢复，未知执行结果（Unknown）需要由可信调用方核实。源码与接口入口见[持久恢复流程](../src/recovery/workflow/service/README.md)。

## 当前流程

1. Queued 查询本地知识库，优先选择适用的可复用脚本。每次复用都需要当前观察、前置条件复核和独立审核；知识库排名不产生执行许可。
2. Diagnosing 通过 `RepairBackend` 请求执行 Harness 结合问题、可信观察和候选形成方案。Harness 是 AI 服务接入；可选外部来源仅提供[只读诊断候选](../src/recovery/knowledge/README.md#外部只读知识库)。
3. AwaitingApproval 保存完整申请意图，再创建审批并保存关联；重复请求不会新增审批。按规则采用人工、Harness 或人工后转 Harness 审核，保存审核尝试与最终决定。
4. Executing 再次复核当前故障、环境与不可绕过的规则，先持久保存执行意图，再使用一次性执行许可，记录外部执行返回的 `ScriptReceipt`。
5. Verifying 使用独立业务验收证据判断成功、失败或 Unknown。执行事实与业务验收结论分别记录，不能从目标健康状态反推动作结果。
6. Publishing 提交方案、条件、执行和验收结果。保存修复经验失败时只重试保存，不重新执行动作。

打开存储只启用本地恢复与查询，不启用执行派发。可信调用方须重新绑定运行期间使用的接口：提交新故障记录前绑定 `IncidentGuard`，提交、恢复、推进、核实执行结果和派发执行许可前绑定 `TargetOwnership`；`KnowledgeSource` 可选。目标所有权与任务登记条件见[领域维护](domain-maintenance.md)。

## 审批关联恢复

`request_plan` 先保存完整方案、观察和稳定的 `ProposedOperation`，任务进入 `AwaitingApproval`，暂时保留 `approval_id = None`；随后创建审批并保存引用，重复请求不新增记录。没有审批引用表示关联尚未完成，不表示已获准。

重新打开恢复流程或同一进程内重试时，使用原操作，包括原任务记录版本号（`revision`）；完整操作及当前规则必须分别与已保存内容完全相同。恢复只补齐原审批引用，方案、观察、操作、复用身份和执行证据保持不可变；不再次诊断，不额外消耗诊断预算，不延长人工截止时间或请求有效期，也不重置决定及许可使用状态。即时保存与读取持久日志恢复使用相同的关联校验。

关联恢复只保存具有最终效力的本地记录，不调用外部执行接口。已批准请求转为 `Paused`，可信调用方须显式 `resume`；执行前仍复核当前故障、观察、完整操作、不可绕过的规则和一次性执行许可。已经使用执行许可或执行结果不明时保持 `Unknown`，不能因关联恢复重新执行。

记录缺少完整方案意图时，不能自动重建关联。完整意图提交前仍可能丢失尚未保存的诊断结果，但已经发生的诊断调用仍计入预算。日志格式校验与显式转换见[完整恢复流程日志迁移](domain-maintenance.md#完整恢复流程日志迁移)。

## 重新诊断与未知执行结果

`max_diagnoses` 限制实际诊断调用次数。只有复用脚本明确执行失败或业务验收失败、执行者已确认停止且仍有预算时，恢复流程才自动重新诊断并创建新审批。新诊断生成的脚本明确失败后进入 `Failed`，即使还有预算也不自动重试。

断线、取消和调用返回不证明目标侧执行已经停止。无法确定执行结果或停止状态时保留 `Unknown`，由可信调用方通过 `RecoveryService::check_result` 分别提交执行证据与独立业务验收证据；已接受的核实记录保存在 `RecoveryTask.result_check`，执行证据时间为 `ExecutionResultCheck.checked_at_ms`。核实结果不放宽审批、一次性执行许可或同一目标的执行互斥。知识库是否保存修复经验也不能证明动作是否执行。
